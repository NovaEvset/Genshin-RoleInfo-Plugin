## 四、Matcha 集成测试

### Matcha 是什么

[Matcha](https://github.com/A-kirami/matcha) 是一个「模拟聊天交互的辅助开发工具」，
使用 **Tauri（Rust + Vue）构建的桌面 GUI 应用**（`package.json` 声明
`"dev": "tauri dev"`、`"build": "tauri build"`），支持 OneBot v11/v12 等协议，
用于在图形界面中创建角色、填写连接信息、手动发送消息并查看原始事件。

### 尝试结果：**未能在本环境运行**

| 尝试 | 结果 |
|---|---|
| 克隆源码 | ✅ 成功（`_upstream/matcha`，v0.4.8） |
| 阅读 README 与协议文档 | ✅ 完成（确认支持 OneBot v11 反向 WS、消息格式要求） |
| 检查构建工具链 | ❌ 缺失：`cargo` / `rustc` 未安装（Tauri 必需） |
| 检查预编译发行包 | ⚠️ GitHub API 触发速率限制，无法枚举 assets；即使存在 `.AppImage`/`.deb`，仍需 GUI 交互 |
| 检查显示环境 | ⚠️ 存在 `DISPLAY=:0`，但 Matcha 的使用流程要求在界面中「新建角色 → 设为 user/bot → 填写连接设置 → 在聊天界面发消息」，无法在无头终端脚本化完成 |

**结论：未使用 Matcha 完成测试，不声称通过 Matcha 测试。**

### 替代方案：协议级等价集成测试（已完成）

由于 Matcha 在协议层做的事就是「作为 OneBot v11 客户端连接机器人、发送事件、
接收回复」，本项目实现了等价的**协议级驱动** `tests/integration/ob11_driver.py`：

- 作为 WebSocket **客户端**连接 NoneBot2 的 OneBot v11 反向 WS 端点
  （必须携带 `X-Self-ID` 头，否则适配器以 403 拒绝——这是实测确认的行为）；
- 发送 `meta_event.lifecycle` 握手；
- 发送真实的群消息 / 私聊消息事件；
- 应答机器人发来的 API 调用（`send_group_msg`、`get_group_member_list`、
  `get_group_member_info`、`get_stranger_info`、`get_private_file_url` 等）；
- 记录机器人实际回复的文本、图片字节数与动作序列。

与 Matcha 的差异：Matcha 需人工点击操作，本驱动将其脚本化。**两者使用同一
协议与同一端点，对被测插件等价。**

### 启动方式

```bash
# 终端 1：启动被测 NoneBot2 实例（反向 WS 端口 18080）
.venv/bin/python tests/integration/bot.py

# 终端 2：运行协议级用例
.venv/bin/python tests/integration/ob11_driver.py --out docs/evidence/integration.json
```

## 七、已知问题与后续建议

### 已知问题

1. **米游社同步为部分实现**
   `米游社更新原神面板` 需通过 `GENSHIN_ROLE_INFO_MYS_PROVIDER` 注入登录态
   提供方（见 README）。未配置时返回配置指引。`mys_sync.py` 的数据转换与
   落盘逻辑已完整迁移，但缺少真实登录态故未做端到端验证。

2. **推荐计算耗时较高**
   实测：单个套装推荐（12⁵ 组合，集束搜索）约 **7.7 秒**；单元测试中
   9⁵ 组合的用例耗时 41.8 秒，其中大部分时间用于反复调用伤害引擎。
   真实缓存较大时单次可达数十秒至数分钟。实现已用 `asyncio.to_thread`
   避免阻塞事件循环，但用户需合理预期响应时间。
   **建议**：为伤害引擎的规则编译结果与中间计算结果增加缓存。

3. **伤害引擎使用 `exec` / `eval`**
   引擎把内置 JSON 中的 JS 规则转译为 Python 后执行。规则文件随包分发
   （MIT 许可，来源为 Miao-Plugin），当前可信；**若替换为可下载/可热更的
   不可信来源，等同于任意代码执行**。
   **建议**：如需热更新规则，增加签名校验或预编译。

4. **评分算法的上游遗留脆弱路径**
   - 有效词条权重为空时，`get_artifact_score` 会抛异常（实测为 `KeyError('0')`，
     而非部分文档所述的 `ZeroDivisionError`）。当前 `score.json` 无全 0 权重角色。
   - 非法副词条名（元素/物理伤害加成、治疗加成）且缺少 `强化次数` 时会
     `KeyError`（`grow_min_value` 仅 10 个键）。
   - `get_effective` 的 `try` 块从第 295 行才开始，缺少 `data["圣遗物"]`
     键会向外抛 `KeyError`（源数据总由 `PlayerInfo` 生成，正常流程不会触达）。

   以上行为已在测试中固化，便于日后回归。

5. **`重置最强` 保持 `block=False`**
   与原项目一致，因此该命令之后的其他匹配器仍可能处理同一条消息。

6. **推荐命令缺少输入反馈**
   当角色名/套装名解析失败时（例如把「昔日宗室之仪」误写成 `宗室套`），
   命令会**静默返回**，用户看不到任何提示。这是源项目的既有行为，
   本次迁移保持了一致性（未擅自改变交互）。
   **建议**：后续可考虑增加「未识别角色/套装」的提示。

### 后续建议

1. 为伤害引擎增加规则编译缓存（`compile_js_function` 目前每次调用都重新
   `exec`），可显著降低推荐与排行的耗时。
2. 补充真实 NapCat + QQ 的端到端测试清单，并在 PR 中提供手工验证步骤。
3. 若上游 `miao-plugin` 更新规则表，可用 `docs/FEATURE_MAPPING.md` 中的
   parity 测试快速确认迁移实现与新版数据仍然一致。
